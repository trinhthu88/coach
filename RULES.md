# Business-rule cross-check: Postgres RLS vs. frontend mirrors

This table exists because the same business rules — profile status gating, role
gating, coachee/coach allowlists, session limits, and module access — are
enforced in two places that don't share code: Postgres migrations
(`supabase/migrations/`) and the React frontend. Nothing currently keeps them
in sync automatically; this is a manual snapshot, last updated 2026-08-30 for
mentoring's programme-defined session limits (§3 Relationship 4, §4, §6),
coachee-to-coachee peer practice (§3 Relationship 5), the enrollment-
cardinality fix (§3 Relationship 5 area / action item 8), and the
`programmes` vs. `coach_programmes` dead-column finding (§4). Regenerate it
(or at least re-check the "At risk" rows) whenever a migration touches
`status`, `*_allowlist`, `*session_limits`, `peer_coaching_opt_in`, or
`user_module_access`.

Legend: ✅ in sync · ⚠️ at risk (works today, no guardrail against drift) · ❌ gap (one side has no mirror).

## 6. Module access (mentoring)

Mentoring is the first feature gated behind a generic, reusable per-user module-access toggle — independent of `role`, and defaulting to **disabled** (admin must opt a user in).

| Rule | Enforced in DB | Enforced in frontend | In sync? |
|---|---|---|---|
| A user has no access to a module until an admin explicitly grants it | `user_module_access` (`20260818130000_*.sql`) — PK `(user_id, module)`, `enabled boolean NOT NULL DEFAULT false`; only admin can INSERT/UPDATE/DELETE, the user can only `SELECT` their own row. `has_module_access(p_user_id, p_module)` (`20260818130100_*.sql`) is the single source of truth — `COALESCE(enabled, false)`, so a missing row reads as disabled | `ProtectedRoute.tsx`'s new `module` prop calls `useModuleAccess()` → `check_has_module_access` RPC and redirects to `/dashboard` if false (admin bypasses, same as the `role`/`roles` gate); `AppLayout.tsx`'s nav filter independently hides the Mentoring nav item when disabled | ✅ Same defense-in-depth pattern as the status/role gates above — route guard *and* nav visibility, not just one. `has_module_access()` is also consulted inside `can_book_mentoring_session()` (§3), so the booking-eligibility RLS policy and the route/nav gate ultimately read the same table. |
| Admin grants/manages module access | `UserModuleAccess: admin manage` policy | `AdminMentoring.tsx`'s access & pairing table — per-user toggle plus bulk-enable-by-role buttons | ✅ Single admin surface, no duplicated logic. |

Mentoring's preparation-file gate is also worth noting here since it's a *stronger* pattern than the rest of this document: `enforce_mentoring_prep_file_before_completion()` / `enforce_mentoring_feedback_requires_prep_file()` (both in `20260818140400_*`/`20260818140500_*.sql`) block the `completed` transition and feedback submission **at the DB level** via triggers, not just a disabled button. This is a deliberate strengthening scoped to mentoring only, per the task's explicit "hard gate" requirement — it does not retrofit the older, frontend-only `canMarkSessionComplete()` gate (`src/hooks/sessions/completionGate.ts`) that regular/peer sessions still rely on. `MentoringSessionDetail.tsx`'s "Join meeting" link is also disabled (frontend-only — there's no DB mutation on "join" to hook a trigger into, since it's just an existing `meeting_url` being opened) until `prep_file_path` is set, closing the gap between the two DB triggers (which only cover completion/feedback, not the join action itself).

## Summary of action items surfaced here

1. **✅ Fixed in Phase 3** (`supabase/migrations/20260810150000_can_book_session_rpc.sql`): `BookSession.tsx`'s coach-as-coachee limit check (§4, row 3) doesn't query the global-default `coach_session_limits` row and hardcodes `4`. Collapsed relationships 1 and 2 (both write to `sessions`) into a single `public.can_book_session(p_coachee_id, p_coach_id)` function that both the `sessions` INSERT RLS policies and a new `check_can_book_session(p_coach_id)` RPC call. `BookSession.tsx` now gates `canSubmit` on that RPC's answer instead of re-deriving eligibility client-side; the display-only usage numbers for the coach-as-coachee branch were also fixed to include the missing global-default fallback query, so even the informational banner can no longer disagree with what's enforced. This also closed a real gap found while writing the function: neither INSERT policy previously checked the session-limit cap at all — only the frontend's disabled button did, so a direct API call could book past the cap. The DB now enforces it too.
2. **✅ Fixed in Phase 3**: relationships 1 and 2 (the `sessions`-table allowlists) now get a friendly pre-submit message via `check_can_book_session` instead of falling through to a raw `error.message` on `42501`; `BookSession.tsx`'s submit handler also special-cases `42501` as a fallback in case eligibility changes between the pre-check and the actual insert. **Not fixed / out of scope for Phase 3**: relationship 3 (peer coaching, a `peer_sessions` insert) still has no friendly `42501` handling — it wasn't folded into `can_book_session()` since it's a different table/shape (open opt-in pool, not a curated pair) and the task scoped Phase 3 to "the coachee↔coach allowlist" rule specifically. Worth a follow-up if peer-session RLS rejections turn out to happen in practice.
3. **⚠️ Still open**: `CoachFindCoach.tsx` and `CoachPeerCoaching.tsx` still each re-query their respective allowlist/opt-in table client-side for *list filtering* (deciding which coaches to display) rather than calling a shared function — `can_book_session()` only answers "can I book this specific coach," it doesn't help filter a list. Left as-is; low risk since both read the same table the RLS policy reads. (Relationship 4's version of this was fixed — see item 4.)
4. **✅ Fixed** (`supabase/migrations/20260818150000_mentoring_get_my_mentors.sql`): unlike item 3 above, mentoring's list-filtering duplication was collapsed into a shared `public.get_my_mentors()` function (`RETURNS TABLE`, pinned to `auth.uid()`, same style as `get_own_coach_invite_slots()`) that `MentoringFindMentor.tsx` now calls via RPC instead of querying `mentoring_allowlist`/`mentor_profiles` and filtering `is_active` in JS. Doing this surfaced a real gap — `can_book_mentoring_session()` didn't check `is_active` at all — which the same migration also fixed, so the list and the booking-eligibility check are now backed by identical logic instead of two independently-maintained copies.
5. **✅ Fixed** (`supabase/migrations/20260830120000_mentoring_session_limits_schema.sql` / `20260830120100_can_book_mentoring_session_limits.sql`): mentoring's "no session-limit cap, by design" state (formerly §4's last row) was a deliberate omission until the task brief was extended to require one. Added programme-defined limits in both directions, following the `coach_programmes`/`programmes` model (not the older `session_limits` pattern) — see §4's two new rows. `can_book_mentoring_session_reason()` returns *which* check failed (not just a boolean) specifically so `MentoringBookSession.tsx` can show "you're at your limit" separately from "this mentor isn't taking new sessions right now," which a plain boolean couldn't distinguish.
6. **⚠️ New, partially open** (`supabase/migrations/20260830140000_coachee_peer_coaching_schema.sql`): Relationship 5 (coachee-to-coachee peer practice) added, mirroring Relationship 3's shape. Schema, RLS, availability publishing, candidate list, and booking flow are complete and working end-to-end. **Not done**: `Sessions.tsx`/`SessionDetail.tsx` were not extended to recognize `coachee_peer_sessions` as a third `kind` — a booked session currently has no confirm/complete/notes/feedback UI anywhere in the app. This is a real gap, not a stylistic one; treat "book a peer practice session" as not fully shippable until it's closed.
7. **✅ Fixed** (`supabase/migrations/20260830150000_fix_enrollment_cardinality.sql`): `coach_programme_enrollments`' `UNIQUE (coach_id)` and `programme_enrollments`' `UNIQUE (coachee_id, programme_id)` both replaced with a partial unique index scoped to `status = 'active'` — the first made a second enrollment (even completed) structurally impossible for a coach, the second let a coachee hold multiple simultaneous active enrollments while blocking re-enrollment in the same programme. Every insert/update call site (`AdminCoaches.tsx`, `useAdminCoacheeMutations.ts`, `useCoacheeProgrammeImport.ts`, `AdminCoachProgrammes.tsx`) now transitions (close old active → completed, insert new active) via a shared `src/lib/enrollmentTransition.ts` instead of bare-inserting or updating `programme_id` in place. `CoacheeProfileSheet.tsx` and `AdminCoachProgrammes.tsx`'s coach table now both show full enrollment history, not just one row. Verified live (no `supabase/tests/` suite exists to add an automated regression test to): second-active-insert-while-one-active rejected (`23505`), completing-then-re-enrolling succeeds, both rows stay readable.
8. **📝 Documented, not fixed** (§4's new "Coach-facing limit columns exist on two tables" row): `programmes.coach_session_limit`/`peer_session_limit`/`peer_given_limit` are dead columns — every enforcement function and the actual admin-UI display read `coach_programmes` instead. `programmes.coachee_session_limit` is the one live exception (sponsor reporting only, not booking enforcement). Investigate-and-document was explicitly the scope for this item; dropping the three dead columns is a safe future follow-up once double-checked against a live schema search, not done here.

**Note for whoever re-reads this**: `can_book_session()` and `check_can_book_session()` restrict themselves to the caller's own id (or an admin) to avoid being usable as a probe for another user's session-limit/allowlist status — see the comment in the migration. The same restriction applies to `can_book_mentoring_session()`/`check_can_book_mentoring_session()`/`get_my_mentors()`/`can_book_mentoring_session_reason()`/`check_can_book_mentoring_session_reason()`/`check_mentoring_session_usage()`. `check_mentoring_given_usage(p_mentor_id)` is the one function in this family that legitimately needs to answer about someone *other* than the caller (a mentee checking a specific mentor's capacity before booking them) — it's scoped instead of self-pinned: it only returns data when the caller is allowlisted with that mentor (or is admin), so it can't be used to probe an arbitrary coach's booking load.
