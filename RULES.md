# Business-rule cross-check: Postgres RLS vs. frontend mirrors

This table exists because the same business rules — profile status gating, role
gating, coachee/coach allowlists, session limits, and module access — are
enforced in two places that don't share code: Postgres migrations
(`supabase/migrations/`) and the React frontend. Nothing currently keeps them
in sync automatically; this is a manual snapshot, last updated 2026-08-18 for
the mentoring module (§3 Relationship 4, §6). Regenerate it (or at least
re-check the "At risk" rows) whenever a migration touches `status`,
`*_allowlist`, `*session_limits`, `peer_coaching_opt_in`, or
`user_module_access`.

Legend: ✅ in sync · ⚠️ at risk (works today, no guardrail against drift) · ❌ gap (one side has no mirror).

## 1. Profile status gating

| Rule | Enforced in DB | Enforced in frontend | In sync? |
|---|---|---|---|
| A user with `status` outside `{active, reach_limit}` is treated as not-yet-usable | No RLS policy blocks reads/writes by `status` directly anymore (see note below) — this is purely a routing/UX rule | `ProtectedRoute.tsx` L40-49: any status other than `active`/`reach_limit` redirects to `/pending` (admin bypasses) | ✅ Frontend-only rule by design; no DB mirror needed since it doesn't gate data access, only navigation. Covered by `src/components/__tests__/ProtectedRoute.test.tsx` for all 6 `user_status` enum values. |
| `reach_limit` must **not** lock a user out of the app (only blocks new bookings) | `enforce_session_completion_limit()` (coachee, `20260430130143_*`) and `enforce_coach_as_coachee_limit()` (coach-as-coachee, `20260430171032_*`) flip `profiles.status` to `reach_limit` when the lifetime cap is hit, and flip it back to `active` when usage drops back below | `ProtectedRoute.tsx` L45 explicitly excludes `reach_limit` from the `/pending` redirect | ✅ In sync, and now has an explicit regression test (`ProtectedRoute.test.tsx`, "reach_limit" case) — previously untested. |
| `must_change_password` forces a password reset before anything else | No DB-level block (Supabase Auth allows sign-in regardless) | `ProtectedRoute.tsx` L33-35 redirects to `/set-new-password` | ❌ Gap: purely a frontend UX gate. If someone bypasses the SPA (calls Supabase REST/RPC directly with a valid session), the DB does not enforce a password change. Low severity since it only gates *first-login UX*, not data access — noted here so it isn't mistaken for a security control. |
| Which profiles a user may `SELECT` | `Profiles: view own`, `Profiles: admin view all`, `Profiles: counterpart via session`, `Profiles: counterpart via allowlist` (`20260501185440_*`), `Profiles: coaches view active coach directory` (`20260807211209_*`) — note the old blanket `Profiles: view active` policy (`status = 'active'`) was **dropped** in `20260501185440_*` | No frontend mirror — pages just query `profiles` and render whatever RLS returns | ✅ Correct by construction: frontend has no duplicate logic to drift, RLS is the sole source of truth. |

## 2. Role-based access

| Rule | Enforced in DB | Enforced in frontend | In sync? |
|---|---|---|---|
| Admins bypass role restrictions everywhere | `public.has_role(auth.uid(), 'admin')` OR-ed into nearly every policy (e.g. `Sessions: admin manage`, `Coach profiles: admin manage`, `Profiles: admin view all` — all in `20260429193745_*`) | `ProtectedRoute.tsx` L51: `role !== "admin"` short-circuits the required-role check; L42-47 also exempts admin from the status redirect | ✅ In sync; covered by `ProtectedRoute.test.tsx` ("allows admins into role-restricted routes", "lets admins through even when status is not active"). |
| Route requires a specific role (`coach`, `coachee`, `admin`) | Table-level RLS policies scoped with `has_role(auth.uid(), '<role>')` (e.g. `Sessions: coachee create own` requires `has_role(..., 'coachee')`) | `App.tsx` passes `role="coach" \| "coachee" \| "admin"` to `<ProtectedRoute>` per route; `ProtectedRoute.tsx` L51-53 redirects to `/dashboard` on mismatch | ✅ In sync for the routes exercised in tests. Worth noting: this is two independently-maintained lists (the RLS policy per table vs. the `role=` prop per `<Route>` in `App.tsx`) — nothing fails loudly if a new admin-only table is added without a matching `role="admin"` route, since the RLS would simply reject reads/writes with no page-level redirect. Not currently testable without an integration/E2E harness. |

## 3. Booking-eligibility allowlists (four separate relationships)

| Rule | Enforced in DB | Enforced in frontend | In sync? |
|---|---|---|---|
| **Relationship 1 — coachee → coach**: a coachee may only book a coach on their admin-curated allowlist | `Sessions: coachee create own` INSERT policy (`20260810120000_enforce_session_allowlists.sql`) requires an `EXISTS` match in `coachee_coach_allowlist`; also gates *visibility* of the coach's profile via `Coach profiles: coachee view allowlisted` (`20260430100320_*`, using `coach_visible_to_coachee()`) | `Coaches.tsx` (coachee's browse page) does **not** re-filter by allowlist client-side — it relies entirely on RLS to only return allowlisted coaches | ✅ In sync, and lower-risk than a duplicate: frontend has no copy of the rule to drift. **But** see the ❌ row below — if a coachee reaches `BookSession.tsx` for a coach they're no longer allowlisted for (stale link, admin just removed them), the INSERT fails with a bare Postgres `42501` and `BookSession.tsx` L282 shows the raw `error.message` (no friendly copy). This is the exact "silent 42501" gap called out for Phase 3. |
| **Relationship 2 — coach-as-coachee**: a coach may only book a mentor coach on their admin-curated allowlist | `Sessions: coach create as coachee` INSERT policy (`20260810120000_*`) requires an `EXISTS` match in `coach_as_coachee_allowlist` | `CoachFindCoach.tsx` L28-42 independently queries `coach_as_coachee_allowlist` and filters the coach list client-side | ⚠️ At risk: this *is* a duplicated round-trip against the same table (not hardcoded logic, so low drift risk), but it means the allowlist-membership check is written in two places. If the DB policy's join condition ever changes (e.g., adds a "pair must also be mutually active" clause), `CoachFindCoach.tsx` won't know and will keep showing coaches the INSERT would reject. Same `42501`-with-raw-message gap as Relationship 1 if that happens. |
| **Relationship 3 — peer coaching**: a coach may only book another coach who has opted in to peer coaching (`coach_profiles.peer_coaching_opt_in`) — intentionally an open pool, not a curated pair | `Peer sessions: peer-coachee create own` INSERT policy (`20260810121500_enforce_peer_opt_in.sql`) requires `coach_profiles.peer_coaching_opt_in = true` for the target | `CoachPeerCoaching.tsx` L29-31 filters candidates with `.eq("peer_coaching_opt_in", true)` | ⚠️ At risk for the same reason as Relationship 2 — duplicated filter condition rather than a shared source. Currently identical, so functionally in sync today. |
| **Relationship 4 — mentoring**: a mentee (either a coachee *or* a coach, unlike relationships 1-3 which are single-role) may only book a mentor on their admin-curated `mentoring_allowlist` pairing, and only if `user_module_access` grants them the `mentoring` module (see §6) | `MentoringSessions: mentee create own` INSERT policy (`20260818140400_mentoring_sessions.sql`) requires `can_book_mentoring_session(auth.uid(), mentor_id)` (`20260818140300_*`), which checks profile status + `has_module_access(mentee_id, 'mentoring')` + an `EXISTS` match in `mentoring_allowlist` — no session-limit cap, unlike relationships 1-2 | `MentoringFindMentor.tsx` queries `mentoring_allowlist` directly, RLS-filtered to the caller's own pairings (same accepted pattern as relationships 2-3) | ⚠️ At risk for the same reason as relationships 2-3 — duplicated allowlist query for list filtering, not a shared source. `MentoringBookSession.tsx` does call `check_can_book_mentoring_session()` as the authoritative pre-submit gate (mirroring `check_can_book_session()`) and handles `23505`/`42501` the same friendly way `BookSession.tsx` does, so the *booking-eligibility* check itself is in sync — only the mentor-list-filtering query is duplicated. |

## 4. Session limits (three separate caps, all treated as *lifetime* totals despite the `monthly_limit` naming)

| Rule | Enforced in DB | Enforced in frontend | In sync? |
|---|---|---|---|
| Regular coachee: lifetime completed-session cap, personal override → global default row → `4` | `enforce_session_completion_limit()` trigger (`20260430130143_*`) + `get_coachee_session_usage()` RPC (`20260429212627_*`) — both use the same `COALESCE(personal, global-NULL-row, 4)` chain | `BookSession.tsx` L190-199 calls `supabase.rpc("get_coachee_session_usage", ...)` directly — no client-side reimplementation | ✅ Fully in sync: frontend calls the DB function instead of duplicating its logic. This is the model the Phase 3 `can_book_session()` RPC should follow for the other two limits below. |
| Coach acting as peer-coachee: lifetime completed-peer-session cap, personal override → global default → `4` | `enforce_coach_as_coachee_limit()` trigger (`20260430171032_*`) + `get_coach_peer_session_usage()` RPC (fixed for lifetime counting in `20260810123000_fix_peer_usage_lifetime.sql`) | `BookSession.tsx` L163-170 calls `supabase.rpc("get_coach_peer_session_usage", ...)` directly | ✅ In sync, same pattern as above. |
| Coach acting as regular coachee (coach-as-coachee, non-peer): lifetime completed-session cap, personal override → global default → `4` | `enforce_coach_as_coachee_limit()` trigger (`20260430171032_*`), same `COALESCE(personal, global-NULL-row, 4)` chain, reused for both the peer and non-peer coach-as-coachee caps | `BookSession.tsx` L172-188 does **not** call an RPC — it manually queries `coach_session_limits.eq("coach_user_id", user.id).maybeSingle()` for the personal override, then separately counts completed `sessions`, and falls back to a **hardcoded `?? 4`** if no personal row exists | ❌ **Real drift bug**: the frontend never queries the global-default row (`coach_session_limits` where `coach_user_id IS NULL`). Today it happens to match because that row's `monthly_limit` is still `4`. If an admin changes the *global* default (not a per-coach override) via the admin UI, `BookSession.tsx`'s displayed usage/limit and its `canSubmit` gate for this one flow will silently stop matching what the DB trigger actually enforces — coaches could see "you can book" and then get a raw `42501`/limit rejection, or vice versa. **This is the concrete case Phase 3's `can_book_session()` RPC should collapse into a single source of truth**, mirroring how the other two limits already call an RPC instead of re-deriving the value. |
| Same limit, shown as informational text (not enforcement) | Same trigger/table as above | `CoachFindCoach.tsx` L43-48 does its own separate query of `coach_session_limits`, with fallback `lim?.monthly_limit ?? 0` (note: **`0`, not `4`** — inconsistent even with `BookSession.tsx`'s own fallback) | ⚠️ Cosmetic-only (this value is just displayed, not enforced), but it's a third independent copy of "resolve a coach's session limit" with a third different fallback constant. Symptom of the same missing shared source. |
| **Mentoring has no session-limit cap, by design** — not requested when the module was built. `can_book_mentoring_session()` (§3, Relationship 4) only checks profile status + module access + allowlist membership; there is no `mentoring_session_limits` table. | n/a | n/a | N/A — deliberate omission, not a gap. Add a limit table + `COALESCE` chain here (mirroring the other three) if mentoring ever needs a cap. |

| Rule | Enforced in DB | Enforced in frontend | In sync? |
|---|---|---|---|

## 6. Module access (mentoring)

Mentoring is the first feature gated behind a generic, reusable per-user module-access toggle — independent of `role`, and defaulting to **disabled** (admin must opt a user in).

| Rule | Enforced in DB | Enforced in frontend | In sync? |
|---|---|---|---|
| A user has no access to a module until an admin explicitly grants it | `user_module_access` (`20260818130000_*.sql`) — PK `(user_id, module)`, `enabled boolean NOT NULL DEFAULT false`; only admin can INSERT/UPDATE/DELETE, the user can only `SELECT` their own row. `has_module_access(p_user_id, p_module)` (`20260818130100_*.sql`) is the single source of truth — `COALESCE(enabled, false)`, so a missing row reads as disabled | `ProtectedRoute.tsx`'s new `module` prop calls `useModuleAccess()` → `check_has_module_access` RPC and redirects to `/dashboard` if false (admin bypasses, same as the `role`/`roles` gate); `AppLayout.tsx`'s nav filter independently hides the Mentoring nav item when disabled | ✅ Same defense-in-depth pattern as the status/role gates above — route guard *and* nav visibility, not just one. `has_module_access()` is also consulted inside `can_book_mentoring_session()` (§3), so the booking-eligibility RLS policy and the route/nav gate ultimately read the same table. |
| Admin grants/manages module access | `UserModuleAccess: admin manage` policy | `AdminMentoring.tsx`'s access & pairing table — per-user toggle plus bulk-enable-by-role buttons | ✅ Single admin surface, no duplicated logic. |

Mentoring's preparation-file gate is also worth noting here since it's a *stronger* pattern than the rest of this document: `enforce_mentoring_prep_file_before_completion()` / `enforce_mentoring_feedback_requires_prep_file()` (both in `20260818140400_*`/`20260818140500_*.sql`) block the `completed` transition and feedback submission **at the DB level** via triggers, not just a disabled button. This is a deliberate strengthening scoped to mentoring only, per the task's explicit "hard gate" requirement — it does not retrofit the older, frontend-only `canMarkSessionComplete()` gate (`src/hooks/sessions/completionGate.ts`) that regular/peer sessions still rely on.

## Summary of action items surfaced here

1. **✅ Fixed in Phase 3** (`supabase/migrations/20260810150000_can_book_session_rpc.sql`): `BookSession.tsx`'s coach-as-coachee limit check (§4, row 3) doesn't query the global-default `coach_session_limits` row and hardcodes `4`. Collapsed relationships 1 and 2 (both write to `sessions`) into a single `public.can_book_session(p_coachee_id, p_coach_id)` function that both the `sessions` INSERT RLS policies and a new `check_can_book_session(p_coach_id)` RPC call. `BookSession.tsx` now gates `canSubmit` on that RPC's answer instead of re-deriving eligibility client-side; the display-only usage numbers for the coach-as-coachee branch were also fixed to include the missing global-default fallback query, so even the informational banner can no longer disagree with what's enforced. This also closed a real gap found while writing the function: neither INSERT policy previously checked the session-limit cap at all — only the frontend's disabled button did, so a direct API call could book past the cap. The DB now enforces it too.
2. **✅ Fixed in Phase 3**: relationships 1 and 2 (the `sessions`-table allowlists) now get a friendly pre-submit message via `check_can_book_session` instead of falling through to a raw `error.message` on `42501`; `BookSession.tsx`'s submit handler also special-cases `42501` as a fallback in case eligibility changes between the pre-check and the actual insert. **Not fixed / out of scope for Phase 3**: relationship 3 (peer coaching, a `peer_sessions` insert) still has no friendly `42501` handling — it wasn't folded into `can_book_session()` since it's a different table/shape (open opt-in pool, not a curated pair) and the task scoped Phase 3 to "the coachee↔coach allowlist" rule specifically. Worth a follow-up if peer-session RLS rejections turn out to happen in practice.
3. **⚠️ Still open**: `CoachFindCoach.tsx` and `CoachPeerCoaching.tsx` still each re-query their respective allowlist/opt-in table client-side for *list filtering* (deciding which coaches to display) rather than calling a shared function — `can_book_session()` only answers "can I book this specific coach," it doesn't help filter a list. Left as-is; low risk since both read the same table the RLS policy reads.

**Note for whoever re-reads this**: `can_book_session()` and `check_can_book_session()` restrict themselves to the caller's own id (or an admin) to avoid being usable as a probe for another user's session-limit/allowlist status — see the comment in the migration.
